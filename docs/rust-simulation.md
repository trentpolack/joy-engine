# Rust Simulation
The headless simulation layer of Joy Engine's Rust crate (`src/environment`, `src/physics`, and `src/gameplay`): the environment clock, rigid-body physics and raycast vehicles, destructible chunk structures, entities, runtime components, systems, and controllers, authored level and object documents with the editor's undo history, the component schema catalog, and the level runtime. It is a port of the TypeScript engine's `src/environment`, `src/physics`, and `src/gameplay` simulation code. It uses only the foundation layer (`src/core`), never content, rendering, or platform modules, and builds identically for native targets and `wasm32-unknown-unknown`.

## Ownership Model
Owners hand out copyable ids and handles instead of references. `PhysicsWorld` issues `BodyHandle` and `VehicleHandle` values stamped with the issuing world's identity, so a handle from another world or a removed body is reported as unknown rather than aliasing a different body. `EntityWorld` owns entities (insertion-ordered), controllers, and systems, and issues `EntityId`, `ControllerId`, and `SystemId` values.

Each `Entity` is split into plain `EntityState`, an optional boxed `EntityBehavior` (what a TypeScript `Entity` subclass would add), and runtime `EntityComponent`s keyed by component type. The world takes the behavior out while it runs, and borrows a component and the state as disjoint fields, so hooks receive `&mut EntityState` plus a `SimulationContext` (a mutable borrow of physics and read access to the entity-to-body and entity-to-vehicle maps) without aliasing their owner. Structural changes from hooks go through `SimulationContext::request_spawn`/`request_remove`. Bodies and vehicles listed for an entity are owned by it (the TypeScript `entity.own`): removing the entity removes them. Component and behavior resources are Rust values released by `Drop`, which replaces the TypeScript `own()` lists.

Lifecycle order matches the TypeScript engine. Spawning registers the entity, attaches a runtime component for every authored component type the `ComponentRegistry` knows (in authored order), and then runs `on_spawn`; a failing `on_attach` detaches that component (running `on_detach`) and rolls back the whole spawn. Removal releases possession, runs `on_destroy`, detaches components in reverse attachment order (each `on_detach`, then drop), removes the entity's bodies and vehicles, and finally drops the behavior. Systems run before behaviors in insertion order and receive `&mut [&mut Entity]` matched by runtime components; `on_add` failures remove the system again (running `on_remove`). `World` is the composition root that owns `EntityWorld`, `PhysicsWorld`, and the handle maps (`World::split` provides the borrows, `World::from_parts` accepts an `EntityWorld` built with a component registry); dropping it removes systems (reverse order), then entities, then physics.

`ChunkStructure` copies its definitions and owns all damage state; queries borrow definitions, and change sets, damage states, and support diagnostics are owned copies. `LevelDocument` owns its level, up to 80 undo snapshots, the redo stack, and the selection; edits run on isolated drafts and `snapshot()` returns owned copies. `ComponentSchemaCatalog` owns registered schemas and lends read-only borrows.

## Physics Backend
Physics uses rapier3d 0.36 with `enhanced-determinism`; identical worlds stepped identically produce bit-identical transforms, and rapier types never appear in the public API. Inputs that feed the solver (Euler rotations and damping coefficients) are computed with rapier's libm-backed scalar math rather than platform math, so native and WebAssembly builds create bit-identical bodies. Stepping keeps the TypeScript accumulator exactly (accumulate, clamp to `fixed_step * max_sub_steps`, step while `accumulator + 1e-12 >= fixed_step`, discard the excess), and each fixed step updates vehicles, steps the solver, and then clears one-step user forces.

`PhysicsWorld` implements the `PhysicsBackend` contract as the engine's CPU backend (the TypeScript contract has no implementation): `apply_mutations` removes listed shape ids and adds static boxes keyed by shape id, atomically, rejecting batches older than the newest applied sequence, duplicate or empty ids, and non-finite or non-positive boxes; `query` casts only against resident shapes and reports world distance; `step` advances the solver. Destructible structures feed it through `create_removal_mutation_batch(change.revision, removed_ids)`, so collision changes at the same boundary as damage, and debris bodies collide with the surviving chunks.

Mapping from cannon-es (the TypeScript backend):
- Mass 0 is a fixed body; planes face +Y before rotation and become rapier half-spaces.
- Friction and restitution combine by multiplication (`CoefficientCombineRule::Multiply`), like cannon's material product.
- Damping `d` is cannon's per-second fraction (`v *= (1 - d)^dt`); rapier uses `v *= 1 / (1 + dt * c)`, so bodies use `c = -ln(1 - d)`, with `d = 1` mapped to a large finite coefficient.
- Bodies never sleep (cannon worlds default to `allowSleep = false`).
- Raycasts test every body against its current pose (so new or teleported bodies are found before the next step) and ignore a body whose shape contains the ray start, like cannon's `skipBackfaces`.
- Vehicles use rapier's `DynamicRayCastVehicleController` (Bullet-derived, like cannon's `RaycastVehicle`) with up = +Y, forward = +Z, ray (0, -1, 0), and axle (-1, 0, 0). Positive throttle drives +Z directly (cannon's tire tangent was -Z, hence the TypeScript negation), positive steer turns toward +X, and wheel spin is reported with cannon's sign so wheels visibly roll forward.

Known gaps against cannon-es:
- `rollInfluence` is validated and stored, but rapier 0.36 keeps it private at 0.1 (the TypeScript default is 0.01).
- Rapier divides rolling and brake friction by the number of grounded wheels before clamping to `brake_force`; braking at the bound matches, gentle rolling resistance is weaker.
- Rapier does not apply the opposite side impulse to a dynamic ground body.
- Wheel rays query rapier's broad phase, which includes a new or moved collider only after the next solver step, so a vehicle created on the same frame as its ground lands one fixed step later.
- Solver details (iterations, contact softness) differ, so trajectories are close but not identical. In the TypeScript suite's drive scenario both engines travel 17.8 m in two seconds at 17.6 m/s.

## Destruction
`ChunkStructure` is solver-independent and keeps the TypeScript arithmetic in `f64` and in the same evaluation order, including V8's `Math.hypot` algorithm (`core::js_hypot`) for support distances, so results match exactly. Damage is queued and applied atomically at `commit()`: overlapping hits accumulate, chunks at zero health leave first, then support is evaluated once and unsupported chunks detach in the same revision (the support diagnostics describe that evaluation). Support is a geometric masonry rule: chunks touching the ground plane anchor, stacked contacts and side-face contacts (never corners) carry support, and horizontal offsets spend the cantilever allowance; a shortest-path search with generation-order tie-breaking resolves reach. Revisions increment only when chunks leave and on every `reset()`. `create_chunk_mesh_data` returns closed boxes as plain `MeshAssetData` (positions, indices, per-vertex material tints, and `chunkCount`/`closedInteriorSurfaces` metadata) for the rendering layer to upload.

## TypeScript Semantics
Preserved: defaults, validation ranges, time units, update order (entities in insertion order; `World` steps physics then entities; `LevelRuntime` updates entities with `min(seconds, 0.1)`, steps physics, then copies body poses into entities), component lifecycle order and rollback, system matching by runtime components, exclusive possession with intent clearing and reset hooks on both sides, entities spawned during an update waiting for the next one, component scaling and rollback, document key order and number formatting (levels round trip byte for byte), `LevelDocument` transactions (validated drafts, order-sensitive no-op detection, an 80-entry history, selection revalidation), schema issue paths and messages, destruction results and messages, and grid-search tie-breaking and settle order.

Parity tests compare against values recorded from the TypeScript engine: the FORM DESTRUCTION example's seeded wall driven by aimed hits and a FRAMEBREAK-style building with the game's collapse rule (every change set, damage state, support distance, ray hit, occupancy query, and mesh value matches exactly), built-in schemas, presets, and every validation message, a `LevelDocument` edit/undo/redo sequence compared as serialized text, and component and system lifecycle order.

Intentional differences:
- Every entity can be possessed; there is no `Character` subclass. `character.rs` holds `ControlIntent` (the TypeScript `controlIntent` record, with `ControlIntent::from_json` for untrusted records) and documents how the `Character` contract maps onto `EntityState`, `EntityWorld`, and `EntityBehavior`. Removing any entity clears its intent and calls `reset_control`.
- `Controller` is the possession-only base; `IntentController` samples intent and covers `PlayerController` and `AIController` (type aliases). Infallible samplers use `IntentController::new`; samplers that can fail (a disconnected device) use `try_new`, and a failed sample leaves the entity without intent, like a throwing TypeScript sampler.
- Runtime components are keyed by the type they were registered or attached under and read their authored record from `EntityState::components`; the TypeScript component instead retained a reference to the record and carried its own `type`. Component factories cannot fail (fallible setup belongs in `on_attach`). Queries with blank component types match nothing instead of throwing.
- `EntityWorld::add_system` returns `Result` and systems cannot be added or removed while systems update.
- Spawn and remove requests made from `on_spawn`/`on_destroy` apply at the start of the next update instead of synchronously. Behavior `update` hooks cannot fail.
- `EntityRegistry::register` returns `Result` (duplicate and blank types fail, like the TypeScript throws); `register_plain` registers a type without behavior. Unregistered types fail to spawn.
- `EntityTransform` stores `f32`; authored transform values needing double precision are rounded to the nearest `f32` and written back in its shortest form.
- `serialize_level` writes as-is (call `LevelData::validate` for edited data); `serialize_object` validates and returns `Result`. `LevelDocument::transact` returns `Result<bool, LevelError>` instead of throwing; `try_transact` forwards edit errors.
- `World` and `LevelRuntime` own their physics world (the TypeScript borrowed-solver option becomes `World::with_physics`/`LevelRuntime::with_physics_options`).
- Queries on removed bodies or vehicles return `None` (or zero/empty) instead of throwing; `raycast` returns `None` for non-finite input. `ChunkStructure::raycast` rejects non-finite origins and directions (TypeScript only checked their length); array-length checks are enforced by the `[f64; 3]` types.
- Mutation batch sequences are `u64`, so the TypeScript negative-sequence check is a type guarantee; `PhysicsBackend` methods are synchronous.
- Component schemas are typed structs (`ComponentFieldKind` is an enum), so the TypeScript checks for non-string labels or unknown kinds happen when deserializing; catalogs store owned copies instead of frozen objects.
- Level presentation (`LevelScene`) lives in the rendering layer (`src/rendering/level_scene.rs`).
