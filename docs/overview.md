# Joy Engine architecture
[Engine documentation](README.md) · [API reference](api/README.md)

## Joy Engine Features
- luma.gl-based backend for providing WebGPU rendering capabilities; falls back on WebGL 2 when WebGPU is unavailable. WebGL 1 is not implemented.
- Supports HDR render targets and tonemapping (default: AgX, also supports ACES).
- A suite of postprocessing effects such as Bloom, Film Grain, and Vignetting.
- Provides easy access for creating per-project game loops.
- Dev tools for development deployments of projects (or the whole site).
- Access to a seeded random stream for consistent results across sessions.
- And more as it comes up.


## Architecture and ownership

See [JavaScript coding standards](coding-standards.md) for the concrete reading model adapted from joygl-ts and JoyCore, including state ownership, module order, public contracts, and cleanup examples.

See [repository architecture](https://github.com/trentpolack/JoyGames/blob/develop/docs/architecture.md) for the engine feature buckets, script organization, configuration format decision, and commenting expectations used across JavaScript and shaders.

The `joy-engine/src` tree is the single engine implementation. All consumers use the `joy-engine` workspace package, whose public API is `joy-engine/src/index.ts`; neither games nor repository tests reach through that package boundary.

Future games can reuse these mechanisms without inheriting SPACE SCUFFLES rules. These modules operate on plain data and browser resources; they do not import project configuration, assets, or gameplay classes.
- `joy-engine/src/simulation/motion.ts`: `accelerateBody` applies acceleration and drag per fixed tick; `moveBody` advances position in the caller's velocity units. Games own steering, collision response, lifetime, and bounds.
- `joy-engine/src/particles/particle-effect.ts`: `ParticleEffect` owns the seconds-based particle simulation used by both games and PARTICLE LAB. Project `.joyfx` assets own the recipes; renderers borrow runtime state. Standalone legacy simulation helpers remain exported but are not used by games.
- `joy-engine/src/rendering/geometry/geometry.ts`: `addTriangle`, `addQuad`, and `addCircle` append triangle-list vertices with an interleaved `x, y, z, r, g, b, a` layout. Radius is measured from center to perimeter (to a corner for triangles and squares). `addMesh` rotates, scales, translates, and tints a `ShadedMesh3D` while preserving each vertex's height. Each shaded model triangle stores three XYZ positions followed by a face brightness multiplier. `addPolygon`, `addRadialPolygon`, `addGradientRadialPolygon`, `addRing`, and `addLine` provide regular and sampled silhouettes, color-feathered particle fans, annuli, and butt-ended thick lines. Ring width is half thickness; line width is full thickness. All coordinates use caller-defined logical units.
- `joy-engine/src/core/color.ts`: `parseHexColor` decodes validated #RGB and #RRGGBB strings; `withAlpha` creates a color with replacement alpha without mutating the source. Palette selection stays in the game.
- `joy-engine/src/core/random.ts`: `createSeededRandom(seed)` returns an independently owned deterministic source. Pass it as the optional final argument to `randomRange` or `randomInteger` to keep cosmetic draw counts independent of gameplay. Seeds are integers normalized to unsigned 32-bit values.
- `joy-engine/src/core/math.ts`: `distanceToRectangleEdge` finds the distance along a ray from a rectangle center, shared by asteroid and encounter placement.
- `joy-engine/src/dcc/glb-mesh-loader.ts`: `loadGlbMesh` and async `parseGlbMesh` use loaders.gl to decode an optionally named indexed triangle mesh into copied `IndexedMesh3D` model-space positions, normals, and indices. URL loading accepts binary GLB and JSON glTF assets with linked buffers; accessors may use unsigned-byte, unsigned-short, or unsigned-int indices. The selected mesh must contain exactly one non-empty primitive with matching finite positions and normals, complete triangles, and in-range indices. Node transforms, materials, and animations are not interpreted. Games own asset URLs, model orientation, normalization, lighting, and camera projection.
- `joy-engine/src/browser/dom.ts`: `requireElement` resolves and validates a typed HTML element during startup. Games own selectors, event binding, and HUD behavior.
- `joy-engine/src/rendering/scene/scene-renderer.ts`: `SceneRenderer` is the standard game and editor-viewport composition root. It owns the common shaders, camera integration, scene preparation, postprocessing, canvas sizing, backend selection, and cleanup. Postprocessing is enabled by default so every normal viewport follows the same linear-scene-to-display path.
- `joy-engine/src/rendering/renderers/gpu-triangle-renderer.ts`: `GpuTriangleRenderer` is the lower-level path for behavior-named project materials and engine adapters that need a different uniform or shading contract. It asks luma.gl for the best available device, preferring WebGPU and explicitly retrying WebGL 2 if device creation fails, and owns pipelines, a shared depth attachment, buffers, canvas configuration, and submission. Call `resize` before rendering and `destroy` when disposing the owner.
- `joy-engine/src/rendering/gpu/gpu-device.ts`: `createGpuCanvasDevice` centralizes explicit WebGPU/WebGL adapter registration, backend selection, optional WebGL fallback, debug/error hooks, and canvas setup. `createPortableShaders` selects WGSL or paired GLSL shaders from the created device rather than browser detection. Use these lower-level helpers when a future renderer does not fit the triangle batch.
- `joy-engine/src/rendering/gpu/dynamic-gpu-buffer.ts`: `DynamicGpuBuffer` retains an owned luma.gl buffer across uploads, grows capacity geometrically, rebinds consumers after replacement, and rejects allocations beyond the device's reported limit. It can support vertex, index, uniform, or copy buffers through an explicit usage mask.
- `joy-engine/src/rendering/postprocessor/`: validates project-owned display tuning and owns the scene-to-display resource pipeline. Bloom is limited to bright extraction and separable blur; the separately named display resolve composes glow before exposure, tone mapping, antialiasing, saturation, contrast, grain, and vignette. AgX is the default display transform, with ACES-fitted and linear display-clamp `none` alternatives. Matching authored WGSL/GLSL programs live under `joy-engine/shaders/rendering/postprocessor/`. The scene uses `rgba16float` when creation, rendering, filtering, and blending are supported, otherwise `rgba8unorm` with reduced highlight range. Bloom radius is a fraction of the shorter viewport axis and remains stable across display densities and aspect ratios. Targets resize with the scene and are released by their renderer owner.
- `joy-engine/src/browser/diagnostics/dev-tools.ts`: provides the development-only FPS, frame-time, optional Chromium heap, renderer, and viewport overlay shared by game entry points. Click its summary or press backquote to open runtime details; production builds leave it disabled.
- `joy-engine/src/rendering/camera/top-down-camera.ts`: `createTopDownOrthographicMatrix` centralizes backend-correct clip-depth projection for fixed cameras, while `sortTopDownTransparentTriangles` preserves authored order at equal depths and sorts planar effects back-to-front. Games still own camera tuning and uniform layouts.

The GLB decoder, shaded mesh batching, geometry primitives, color utilities, rectangle-edge math, and DOM lookup were promoted during explicit engine consolidation passes: each is independent of game rules and provides a reusable mechanism for future projects.

The GPU helpers follow luma.gl's Device-first model: capabilities come from the created device, durable resources are allocated outside the frame path, usage flags state their intended operations, resources have debug IDs, and engine-owned resources are destroyed by their owner. Both current projects use the shared post-processing contract. Higher-level luma.gl systems such as render graphs, picking, instancing, and compute remain intentionally unwrapped until a game establishes a concrete reusable contract for them.

**SPACE SCUFFLES** retains its impact-flash shader, palette, entity drawing, explosion asset content, and combat rules. The behavior-named shader is a deliberate exception because its gameplay-driven flash uses a project uniform. luma.gl stays behind the engine renderer so games exchange plain vertex and uniform data rather than GPU handles. Its motion values remain per fixed tick, preserving the existing 60 Hz tuning and the order of acceleration, movement, and damping.

Opaque geometry writes depth; translucent geometry tests it and blends using straight-alpha source-over without writing depth. Games supply translucent triangles sorted back-to-front for their camera as the fourth argument to `GpuTriangleRenderer.render`. The framebuffer and both pipelines use `depth24plus`; every frame clears depth to 1. Projection and near/far ranges remain the game's responsibility. SPACE SCUFFLES supplies an orthographic view-projection matrix that accounts for WebGPU and WebGL clip-depth ranges.

## Luma.gl capability boundary
Joy Engine owns canvas/device setup, lifecycle, portable project shaders, and game-facing data contracts while delegating GPU resources and pipelines to luma.gl. Projects can import the engine's curated luma.gl effects exports—including multiscale bloom, Gaussian blur, tone mapping, FXAA, TAA, SSAO, outlines, and motion blur—from `joy-engine`; projects must not import luma.gl directly. Image effects support WebGPU and WebGL 2; upstream SSAO, TAA, and motion blur currently require WebGPU. `SceneEffects` reports availability and validates their borrowed frame inputs.

The integrated postprocessor now delegates its full pass graph and multiscale bloom to luma.gl's `ShaderPassRenderer`. Joy Engine owns scene attachments, profile translation, supplemental portable modules, and explicit cleanup. `createPortableShaders` uses Shadertools GLSL/WGSL assemblers, including supplied module dependencies; both assemblers are also exported for advanced engine consumers. See [postprocessing](postprocessing.md) for ordering, frame contracts, and fallback behavior.

Development overlays borrow `GpuTriangleRenderer`/`SceneRenderer` through `DevTools.setRenderer`. Their `getDiagnostics({memory, resources})` methods copy existing luma allocation/resource counters only when requested; they do not query the GPU, reset shared counters or add frame instrumentation. Counters aggregate all luma devices in the JavaScript realm and tracked allocations exclude untracked browser/driver memory. See [development diagnostics](https://github.com/trentpolack/JoyGames/blob/develop/docs/development/README.md) for sampling, browser support and disclosure groups.
